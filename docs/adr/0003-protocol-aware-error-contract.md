# 协议感知的网关错误契约

网关此前把同一个上游错误在 Chat、Messages、Responses 三条路径上处理成三种结果：Chat/Responses 只保留上游 400/422，其余 4xx/5xx 折叠成 502；Messages 原样透传；Responses 没有瞬态重试。客户端因此无法区分「请求错了」「权限不够」「模型不存在」「上游过载」「网关超时」，会把不可重试的 403/404 当成可重试的 502 反复重放。我们决定让网关成为协议感知的错误出口：统一错误信封，保留上游 4xx/5xx 状态并按客户端协议重建错误体，401 仍转网关自己的 503 重新认证；重试按 Magpie 的两层语义拆分，同一候选只对瞬态错误重试，402/403 只探测一次，400/422 仅在文字表示瞬态时探测一次；`Retry-After` 超过 8 秒直接返回状态而不重试；403 认证文字触发每请求最多一次重登录；405/415/408 在本地补齐；错误加 `no-store`、`X-Request-Id`，最终失败日志加 `tries`/`physical_attempts`；Responses 增加预提交暂存。选这个方案，是因为本程序只有一个 UM 上游，不能照搬 Magpie「换账号/换 provider/换模型」的候选切换；照搬状态列表只会重发同一个注定失败的请求。

**Status**: accepted

## Considered Options

- **维持现状**：三条路径三种行为，客户端无法判断该不该重试；放弃。
- **照搬 Magpie 的状态列表**：把 401/402/403/404 也加入同一候选重试；但 Magpie 的这些状态属于「换候选」，本程序没有候选可换，重发同一请求不会改变结果；放弃。
- **状态和 body 全部原样透传**：UM 的 `{"detail": ...}` 不是 OpenAI/Anthropic 形状，SDK 读不到 `error.message`；放弃。
- **保留状态、重建 body、按 Magpie 意图拆分重试**：采用。402/403 只探测一次，400/422 条件探测一次，408/429/5xx/传输/超时用完整预算；最终状态保留。

## Consequences

- 客户端能按状态码正确决定是否重试；403/404 不再变成可重试的 502。
- `Retry-After` 超过 8 秒时网关不再提前重试，而是把等待时间交给客户端；分享准入 429 也带等待信号。
- 重登录每逻辑请求最多一次，认证等待计入 540 秒总预算，避免请求被登录轮次占住 30 分钟。
- 分享请求体 32 MiB 上限保留；这是公网入口的自我保护，不是 UM 的限制。
- 本批不做脱敏；`detail.upstream_message` 保留上游原文但有界。这是一个明确决定，不是遗漏。
- 8001 控制台的错误形状不变；本决策只覆盖网关的 HTTP 错误面。
- Python 8000/8100 先落地；云端 8003 Rust 按同一契约补齐，切换前以本文和 spec 为单一事实来源。
