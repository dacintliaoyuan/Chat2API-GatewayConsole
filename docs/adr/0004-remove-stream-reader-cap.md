# 取消网关流式读取并发上限

网关此前用 128 个 reader 槽位限制同时进行的流式或聚合读取；槽位满时返回 503 `too_many_concurrent_streams`。这个上限保护线程和上游连接，但它把容量问题变成客户端可见的 503，而且 128 对本地自用和云端分享是同一个硬编码值。我们决定取消 reader 槽位上限：本地 8000 与云端 8100/8003 都不再限制流式读取并发，`too_many_concurrent_streams` 标记 retired；线程、连接和内存由操作系统与 UM 兜底。HTTP 监听 backlog 从 5 提到 128；认证等待槽位保持 128（可配置）；云端分享准入的每 Key/全局并发保持现状。

**Status**: accepted

## Considered Options

- **保持 128**：干净 503，但用户明确要求取消。
- **提高到 256/512**：只是推迟 503，仍需维护一个任意数字。
- **完全取消**：采用；代价是失败从 503 变成 OS/UM 的拒绝，诊断更差。

## Consequences

- 大量并发流不再收到 503 `too_many_concurrent_streams`；如果 UM 先限流，客户端看到 UM 的 429/500。
- 取消的 reader 仍可能活最多 180 秒；没有本地上限时线程和连接数由 OS 兜底。
- 认证等待 128 和分享准入的每 Key/全局并发不受影响；它们不是同一层。
- 云端 8003 Rust 不得再加 reader 并发上限。
